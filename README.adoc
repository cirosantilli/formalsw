== Install

Install the cleanxyz Python library:

----
pipx install cleanxyz
----

Install Elan, Lean's version manager. On Linux:

----
curl https://elan.lean-lang.org/elan-init.sh -sSf | sh
----

Installation details for other systems: https://github.com/leanprover/elan

Now test it on a hello world link:tests/pass/range_sum.py[]:

----
cleanxyz tests/pass/range_sum.py
----

and if all went well you should see a message:

----
All 3 checks passed
----

and exit status 0.

== Getting started

Consider the following two alternative implementations of the sum of integers 0 to n, one naive and one optimized:

tmp.py

----
def sum(n: int) -> int:
    if n <= 0:
        return 0
    return (n * (n - 1)) // 2

def sum_naive(n: int) -> int:
    total = 0
    for i in range(n):
        total += i
    return total
----

and then suppose that your goal is to formally prove that for every possible input both functions return the same output, i.e. that the functions are equivalent.

Traditionally, the only way to test this would be to add some tests and hope to catch all the edge cases:

----
for i in [1, 2, 3, 10]:
    assert sum(i) == sum_naive(i)
----

but you can never cover all possible input values like that.

This is exactly what formal verification allows you to do.

To specify that we want both function to be proven to be the same, we can add a magic docstrings property to one of them:

----
def sum(n: int) -> int:
    """
    @cleanxyz: Not Throws
    @cleanxyz: Equiv(sum_naive)
    """
    if n <= 0:
        return 0
    return (n * (n - 1)) // 2

def sum_naive(n: int) -> int:
    """
    @cleanxyz: Not Throws
    """
    total = 0
    for i in range(n):
        total += i
    return total
----

After this is specified, if you run:

----
cleanxyz tmp.py
----

it blows up with:

----
error: tmp.py:4: missing proof file tmp.py.lean for `@cleanxyz: Not Throws`
----

which is good because haven't proven what we said we wanted to prove yet!

To create the required proofs, we must create a tmp.py.lean file containing the following theorems:

----
import «.cleanxyz».tests.pass.«range_sum.py.ast»
import CleanXYZ

namespace Tmp

theorem sum_not_throws :
    Not (CleanXYZ.Property.Function.Throws RangeSumAst.module "sum") := by
  sorry

theorem sumNaive_not_throws :
    Not (CleanXYZ.Property.Function.Throws RangeSumAst.module "sum_naive") := by
  sorry

theorem sum_equiv_sumNaive (n : Int) :
    CleanXYZ.PyAst.evalUnaryIntFunction
        RangeSumAst.module "sum" n =
      CleanXYZ.PyAst.evalUnaryIntFunction
        RangeSumAst.module "sum_naive" n := by sorry

end Tmp
----

And now we can try again:

----
cleanxyz tmp.py
----

but this time it fails with:

----
error: tmp.py.lean:11: proof uses `sorry`
----

because we cheated with `sorry` which tells Lean to skip a proof.

The final passing proof is something like the following ungodly file. I don't expect you to read and understand it.

The beauty of is is, and the entire reason for this project existing, of course, that you don't need to write that by yourself. You can just ask an LLM to do it for you! 

You only need to understand the definition of properties that you care about in the comments of the source code.

Then you let the LLM loose, and so long as the LLM does not touch your .py source files during the proof step, only the .lean ones, the our scripts and the Lean formal system ensures that the property is true.

Here's the file:

----
import «.cleanxyz».«tmp.py.ast»
import CleanXYZ

namespace Tmp

/-- `sum` returns an integer for every integer input. -/
theorem sum_returns (n : Int) :
    ∃ value,
      CleanXYZ.PyAst.evalUnaryIntFunction
          TmpAst.module "sum" n =
        some value := by
  by_cases hn : n <= 0
  · refine ⟨0, ?_⟩
    simp [
      CleanXYZ.PyAst.evalUnaryIntFunction,
      CleanXYZ.PyAst.Module.findFunctionBody,
      CleanXYZ.PyAst.findFunctionBodyIn,
      CleanXYZ.PyAst.evalIntBlock,
      CleanXYZ.PyAst.evalBoolExpr,
      CleanXYZ.PyAst.evalIntExpr,
      CleanXYZ.PyAst.Env.get?,
      CleanXYZ.PyAst.evalCmpOp,
      TmpAst.module,
      hn,
    ]

  · refine ⟨CleanXYZ.PyAst.sumRange n.toNat, ?_⟩
    simp [
      CleanXYZ.PyAst.evalUnaryIntFunction,
      CleanXYZ.PyAst.Module.findFunctionBody,
      CleanXYZ.PyAst.findFunctionBodyIn,
      CleanXYZ.PyAst.evalIntBlock,
      CleanXYZ.PyAst.evalBoolExpr,
      CleanXYZ.PyAst.evalIntExpr,
      CleanXYZ.PyAst.Env.get?,
      CleanXYZ.PyAst.evalCmpOp,
      TmpAst.module,
      hn,
    ]

theorem sum_not_throws :
    Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum") := by
  rintro ⟨n, hthrow⟩
  obtain ⟨value, hvalue⟩ := sum_returns n
  rw [hthrow] at hvalue
  contradiction

/-- `sum_naive` returns an integer for every integer input. -/
theorem sumNaive_returns (n : Int) :
    ∃ value,
      CleanXYZ.PyAst.evalUnaryIntFunction
          TmpAst.module "sum_naive" n =
        some value := by
  refine ⟨CleanXYZ.PyAst.sumRange n.toNat, ?_⟩
  simp [
    CleanXYZ.PyAst.evalUnaryIntFunction,
    CleanXYZ.PyAst.Module.findFunctionBody,
    CleanXYZ.PyAst.findFunctionBodyIn,
    CleanXYZ.PyAst.evalIntBlock,
    CleanXYZ.PyAst.evalIntExpr,
    CleanXYZ.PyAst.evalRangeContribution,
    CleanXYZ.PyAst.Env.get?,
    TmpAst.module,
  ]

theorem sumNaive_not_throws :
    Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum_naive") := by
  rintro ⟨n, hthrow⟩
  obtain ⟨value, hvalue⟩ := sumNaive_returns n
  rw [hthrow] at hvalue
  contradiction

/-- `sum` and `sum_naive` give the same result for every integer input. -/
theorem sum_equiv_sumNaive (n : Int) :
    CleanXYZ.PyAst.evalUnaryIntFunction
        TmpAst.module "sum" n =
      CleanXYZ.PyAst.evalUnaryIntFunction
        TmpAst.module "sum_naive" n := by
  by_cases hn : n <= 0
  · simp [
      CleanXYZ.PyAst.evalUnaryIntFunction,
      CleanXYZ.PyAst.Module.findFunctionBody,
      CleanXYZ.PyAst.findFunctionBodyIn,
      CleanXYZ.PyAst.evalIntBlock,
      CleanXYZ.PyAst.evalBoolExpr,
      CleanXYZ.PyAst.evalIntExpr,
      CleanXYZ.PyAst.evalRangeContribution,
      CleanXYZ.PyAst.sumRange,
      CleanXYZ.PyAst.Env.get?,
      CleanXYZ.PyAst.evalCmpOp,
      TmpAst.module,
      hn,
      Int.toNat_of_nonpos hn,
    ]
  · simp [
      CleanXYZ.PyAst.evalUnaryIntFunction,
      CleanXYZ.PyAst.Module.findFunctionBody,
      CleanXYZ.PyAst.findFunctionBodyIn,
      CleanXYZ.PyAst.evalIntBlock,
      CleanXYZ.PyAst.evalBoolExpr,
      CleanXYZ.PyAst.evalIntExpr,
      CleanXYZ.PyAst.evalRangeContribution,
      CleanXYZ.PyAst.Env.get?,
      CleanXYZ.PyAst.evalCmpOp,
      TmpAst.module,
      hn,
    ]

end Tmp
----

and now if you run:

----
cleanxyz tmp.py
----

there's no output, which means that all proofs were verified!

----

----

== Specification language

The specification language is how you specify the properties of the program which must be proven.

Specifications are written as markers inside Python docstrings in lines starting with:

----
@cleanxyz
----

There are two types of ways to write the specification:

* <<dsl>>: what most people will use. Easy to learn and obvious.
* <<raw-lean-specification>>. Hard to learn but more general than the DSL.

=== DSL

DSL expressions consist of a property, optionally preceded by one or more `Not` words. For example, `Not Throws` requires a proof of the Lean proposition `Not (Throws ...)`, while `Not Not Throws` negates it twice. The generated theorem name includes each negation, such as `sum_not_throws` or `sum_not_not_throws`.

==== Not

`Not` negates the complete DSL expression following it. It can be applied to any DSL property and can be nested:

[source,python]
----
def sum(n: int) -> int:
    """
    @cleanxyz: Not Throws
    @cleanxyz: Not Equiv(other_sum)
    """
    return n + 1
----

The first marker above requires `sum_not_throws`; the second requires `sum_not_equiv_otherSum`.

==== Throws

`Throws` states that there is at least one integer input for which evaluation fails. Example: link:tests/pass/throws.py[].

[source,python]
----
def reject_odd(n: int) -> int:
    """
    @cleanxyz: Throws
    """
    if n % 2 != 0:
        raise ValueError("odd input")
    return n
----

This marker requires a theorem named `rejectOdd_throws` with type:

[source,lean]
----
CleanXYZ.Property.Function.Throws ThrowsAst.module "reject_odd"
----

which expands to:

[source,lean]
----
∃ n : Int,
  CleanXYZ.PyAst.evalUnaryIntFunction ThrowsAst.module "reject_odd" n = none
----

Use `Not Throws` to state that no input throws. For a function named `sum`, this requires a theorem named `sum_not_throws` with type:

[source,lean]
----
Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum")
----

==== Equiv

`Equiv` states that two functions have identical evaluation results for every input. Example: link:tests/pass/range_sum.py[].

[source,python]
----
def sum(n: int) -> int:
    """
    @cleanxyz: Equiv(sum_naive)
    """
    # ...
----

This marker requires `sum_equiv_sumNaive` with type:

[source,lean]
----
CleanXYZ.Property.Function.Equiv TmpAst.module "sum" "sum_naive"
----

`Equiv` compares the complete `Option Int` results, so two failures are equal. Combine it with `Not Throws` markers when both functions must also return successfully for every input.

=== Raw Lean specification

If the specification starts with "theorem", then it is interpretred as an arbitrary Lean code to be proven.

[source,python]
----
def f(n: int) -> int:
    """Identity function.

    @cleanxyz: theorem f_returns_input (n : Int) :
      n = n ∧ RawLeanAst.module.findFunctionBody "f" ≠ none
    """
    return n
----

Continuation lines are included until a blank line or another marker.

An unqualified theorem name is placed in the proof namespace derived from the Python file path.

Raw theorem markers may also appear in a module docstring; module docstrings do not support the function-specific short forms.

== How it works

The way it all works is as follows. When you run:

----
cleanxyz tmp.py
----

it will determine where to create the `.cleanxyz` directory. When you are inside a .git repository, `.cleanxyz` is always placed next to the `.git`. You basically always  want to use Git becuse you want to check that you LLMs haven't mofidifed your specifications in source files.

Then, inside the `.cleanxyz` directory, `cleanxyz` converts the input Python source code to a versioned JSON AST under `.cleanxyz/tmp.py.ast.json`. This is the language-neutral interchange artifact, so a future converter only needs to produce the same JSON schema.

The adjacent `.cleanxyz/tmp.py.ast.lean` is only a small import bridge. Lean reads the JSON with `include_str`, validates `schema_version`, and elaborates it into a typed `CleanXYZ.PyAst.Module`. Proofs therefore continue to use `TmpAst.module` and operate on the typed data structure, not on untrusted claims made by the converter.

Compiled Lean `.olean` files are written to a mirrored cache under `.cleanxyz/olean/`. `LEAN_PATH` includes that cache, so later proof imports use the compiled modules without placing build artifacts beside checked-in `.lean` proofs.

The top-level JSON shape is:

[source,json]
----
{
  "schema_version": 1,
  "ast": {
    "type": "Module",
    "body": []
  }
}
----

Nodes use a `type` discriminator and fields close to Python's `ast` names. For example, a name expression is `{"type": "Name", "id": "n"}` and a constant is `{"type": "Constant", "value": 1}`.

At the same time, cleanxyz searches for `@cleanxyz:` markers in Python docstrings, and when those are found, it dumps them under `.cleanxyz/tmp.py.reqs.lean` in such a way that unless proof of each requirement is also found, things will blow up when Lean runs.

----
example :
    Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum")
  := Tmp.sum_not_throws

example :
    CleanXYZ.Property.Function.Equiv TmpAst.module "sum" "sum_naive"
  := Tmp.sum_equiv_sumNaive

example :
    Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum_naive")
  := Tmp.sumNaive_not_throws
----

Finally, cleanxyz runs Lean putting everything together:

* `.cleanxyz/tmp.py.ast.json` with the language-neutral AST representation
* `.cleanxyz/tmp.py.ast.lean` with the small JSON-to-Lean import bridge
* `.cleanxyz/tmp.py.reqs.lean` mentioned above with the proof requirements
* `tmp.py.lean` which is supposed to contain your proof
* link:CleanXYZ.lean[] which defines the Python AST representation and properties of the Python language which are then used in correctness proofs
