== Install

Install the cleanxyz Python library:

----
pipx install cleanxyz
----

Install Elan, Lean's version manager. On Linux:

----
curl https://elan.lean-lang.org/elan-init.sh -sSf | sh
----

Installation details for other systems: https://github.com/leanprover/elan

Now test it on a hello world link:tests/pass/range_sum.py[]:

----
cleanxyz tests/pass/range_sum.py
----

and if all went well you should see a message:

----
All 4 checks passed
----

and exit status 0.

== Getting started

Consider the following two alternative implementations of the sum of integers 0 to n, one naive and one optimized:

tmp.py

----
def sum(n: int) -> int:
    if n <= 0:
        return 0
    return (n * (n - 1)) // 2

def sum_naive(n: int) -> int:
    total = 0
    for i in range(n):
        total += i
    return total
----

and then suppose that your goal is to formally prove that for every possible input both functions return the same output, i.e. that the functions are equivalent.

Traditionally, the only way to test this would be to add some tests and hope to catch all the edge cases:

----
for i in [1, 2, 3, 10]:
    assert sum(i) == sum_naive(i)
----

but you can never cover all possible input values like that.

This is exactly what formal verification allows you to do.

To specify that we want both function to be proven to be the same, we can add a magic docstrings property to one of them:

----
def sum(n: int) -> int:
    """
    @cleanxyz: Not Throws
    @cleanxyz: Equiv(sum_naive)
    """
    if n <= 0:
        return 0
    return (n * (n - 1)) // 2

def sum_naive(n: int) -> int:
    """
    @cleanxyz: Not Throws
    """
    total = 0
    for i in range(n):
        total += i
    return total
----

After this is specified, if you run:

----
cleanxyz tmp.py
----

it blows up with:

----
error: tmp.py:4: missing proof file tmp.py.lean for `@cleanxyz: Not Throws`
----

which is good because haven't proven what we said we wanted to prove yet!

To create the required proofs, we must create a tmp.py.lean file containing the required theorems. The stubs can be generated automatically with:

----
./cleanxyz --stub tmp.py > tmp.py.lean
----

which produces:

----
import «.cleanxyz».«tmp.py.ast»
import CleanXYZ

theorem Tmp.sum_not_throws :
    Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum")
  := by
  sorry

theorem Tmp.sum_equiv_sumNaive :
    CleanXYZ.Property.Function.Equiv TmpAst.module "sum" "sum_naive"
  := by
  sorry
----

And now if we try again:

----
cleanxyz tmp.py
----

but this time it fails with:

----
proof check failed for tmp.py
Complete tmp.py.lean; remove any `sorry`; and make sure it compiles before checking requested proof obligations.
Expected proof obligations:
  Tmp.sum_not_throws :
    Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum")
  Tmp.sum_equiv_sumNaive :
    CleanXYZ.Property.Function.Equiv TmpAst.module "sum" "sum_naive"
Lean diagnostic:
  tmp.py.lean:4:8: error: declaration uses `sorry`
  tmp.py.lean:9:8: error: declaration uses `sorry`
error: tmp.py.lean:7: proof uses `sorry`
----

because we cheated with `sorry` which tells Lean to skip a proof.

The final passing proof is an ungodly long file.

But I don't expect you to read and understand and even less write it.

The beauty of is is, and the entire reason for this project existing, of course, that you don't need to write that by yourself. You can just ask an LLM to do it for you! 

You only need to understand the definition of properties that you care about in the comments of the source code.

Then you let the LLM loose, and so long as the LLM does not touch your .py source files during the proof step, only the .lean ones, the our scripts and the Lean formal system ensures that the property is true.

Once the proof is complete, when you run:

----
cleanxyz tmp.py
----

there's no output, which means that all proofs were verified!

You can check this with the following example contained in-tree:

link:tests/pass/range_sum.py[]

----
cleanxyz tests/pass/range_sum.py
----

which has a proof at link:tests/pass/range_sum.py.lean[].

== Further usage

Directories are also accepted; every `.py` file under the directory is checked:

[source,sh]
----
./cleanxyz tests/pass
----

Generate a complete Lean proof-file stub on standard output with `-S` or `--stub`:

[source,sh]
----
./cleanxyz --stub myfile.py > myfile.py.lean
----

The stub imports the generated AST module and declares every requested theorem with `by sorry`. Replace each `sorry` with a proof before running the normal check.

== Specification language

The specification language is how you specify the properties of the program which must be proven.

Specifications are written as markers inside Python docstrings in lines starting with:

----
@cleanxyz
----

There are two types of ways to write the specification:

* <<dsl>>: what most people will use. Easy to learn and obvious. Gets translated to an equivalent Lean long form behind the scenes.
* <<raw-lean-specification>>. Hard to learn but more general than the DSL.

=== DSL

The DSL specification is a magic custom and very simple language that allows specifying commonly used properties easily.

The DSL gets converted to corresponding Lean code behind the scenes.

==== Not

`Not` negates the complete DSL expression following it. For example, to state that a function does not <<throws,throw>> for any input:

my_not_example.py

[source,python]
----
def sum(n: int) -> int:
    """
    @cleanxyz: Not Throws
    """
    return n + 1
----

The marker above requires `sum_not_throws`. `Not` can prefix any other DSL property recursively; for example, `Not Not Throws` has the usual double negation meaning.

==== Throws

`Throws` states that there is at least one input for which the function throws.

Example:

my_throws_example.py

[source,python]
----
def reject_odd(n: int) -> int:
    """
    @cleanxyz: Throws
    """
    if n % 2 != 0:
        raise ValueError("odd input")
    return n
----

This marker requires a theorem named `rejectOdd_throws` with type:

[source,lean]
----
CleanXYZ.Property.Function.Throws MyThrowsExampleAst.module "reject_odd"
----

which expands to:

[source,lean]
----
∃ n : Int, ∃ exception,
  CleanXYZ.PyAst.evalUnaryIntFunctionOutcome ThrowsAst.module "reject_odd" n =
    some (.error exception)
----

Use `Not Throws` to state that no input throws. For a function named `sum`, this requires a theorem named `sum_not_throws` with type:

[source,lean]
----
Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum")
----

==== Equiv

`Equiv` states that two functions have identical evaluation results for every input, i.e. that either:

* both functions return the same value if they return
* both functions throw the same exception if they throw

Example:

[source,python]
----
def sum(n: int) -> int:
    """Optimized version of sum_naive.

    @cleanxyz: Equiv(sum_naive)
    """
    if n <= 0:
        return 0
    return (n * (n - 1)) // 2

def sum_naive(n: int) -> int:
    """Sum of integers from 1 to n. Return 0 if n <= 0."""
    total = 0
    for i in range(n):
        total += i
    return total
----

This marker requires `sum_equiv_sumNaive` with type:

[source,lean]
----
CleanXYZ.Property.Function.Equiv TmpAst.module "sum" "sum_naive"
----

For every input, `Equiv` requires one common exception-aware outcome:

[source,lean]
----
∀ n : Int, ∃ outcome,
  CleanXYZ.PyAst.evalUnaryIntFunctionOutcome TmpAst.module "sum" n =
      some outcome ∧
    CleanXYZ.PyAst.evalUnaryIntFunctionOutcome TmpAst.module "sum_naive" n =
      some outcome
----

An outcome is either `.ok value` or `.error exception`. Successful executions must therefore return the same integer, while throwing executions must have structurally equal exception objects: the same exception class name and equal evaluated positional arguments. An unsupported AST evaluates to `none`, which cannot satisfy `Equiv` even when both sides are unsupported. See link:tests/pass/equiv_throw.py[] for an equivalence proof covering both returns and throws.

For functions annotated with one `list` argument, `Equiv` quantifies over every `List Int` input and requires the same output list. See link:tests/pass/sort.py[] for merge-sort and quicksort equivalence.

==== BigO

`BigO` states the worst-case asymptotic termination cost of a function. Its first argument is an arbitrary Lean expression, so the set of bounds is not hardcoded. Variables used by that expression must be introduced by an explicit input-size binding. For example, `n = len(values)` introduces the Lean variable `n : Nat` and binds it to the length of the Python argument `values`:

[source,python]
----
def merge_sort(values: list) -> list:
    """
    @cleanxyz: BigO(n * (Nat.log2 n + 1), n = len(values))
    """
    # ...
----

This marker requires `mergeSort_bigO` with type:

[source,lean]
----
CleanXYZ.Property.Function.BigO
  SortAst.module "merge_sort"
    (CleanXYZ.PyAst.InputSize.listLength "values")
    (fun n : Nat => n * (Nat.log2 n + 1))
----

The analyzer checks that `values` is the actual `list` argument; changing the binding to another name does not produce a provable obligation. For an integer argument, write `BigO(n, n = input)`. It uses the natural-number projection of the Python integer `input`. The currently supported input measures are thus `n = argument` and `n = len(argument)`.

Other valid bounds include `BigO(1, n = input)`, `BigO(n * n, n = len(values))`, or a call to a user-defined Lean cost function. Because the bound is Lean rather than a second expression DSL, ordinary Lean functions and notation are available.

The cost model assigns cost 1 to every represented statement and expression operation. It then proves a constant multiple of the selected bound beyond some input-size threshold. Calls are unit-cost by default too; later standard-library models can replace that default with operation-specific complexity. The initial structural analyzer recognizes constant and iterative integer functions plus the recursive list-sort shapes demonstrated in link:tests/pass/sort.py[].

=== Raw Lean specification

If the specification starts with "theorem", then it is interpretred as an arbitrary Lean code to be proven.

[source,python]
----
def f(n: int) -> int:
    """Identity function.

    @cleanxyz: theorem f_returns_input (n : Int) :
      n = n ∧ RawLeanAst.module.findFunctionBody "f" ≠ none
    """
    return n
----

Continuation lines are included until a blank line or another marker.

An unqualified theorem name is placed in the proof namespace derived from the Python file path.

Raw theorem markers may also appear in a module docstring; module docstrings do not support the function-specific short forms.

== How it works

The way it all works is as follows. When you run:

----
cleanxyz tmp.py
----

it will determine where to create the `.cleanxyz` directory. When you are inside a .git repository, `.cleanxyz` is always placed next to the `.git`. You basically always  want to use Git becuse you want to check that you LLMs haven't mofidifed your specifications in source files.

Then, inside the `.cleanxyz` directory, `cleanxyz` converts the input Python source code to a versioned JSON AST under `.cleanxyz/tmp.py.ast.json`. This is the language-neutral interchange artifact, so a future converter only needs to produce the same JSON schema.

The adjacent `.cleanxyz/tmp.py.ast.lean` is only a small import bridge. Lean reads the JSON with `include_str`, validates `schema_version`, and elaborates it into a typed `CleanXYZ.PyAst.Module`. Proofs therefore continue to use `TmpAst.module` and operate on the typed data structure, not on untrusted claims made by the converter.

Compiled Lean `.olean` files are written to a mirrored cache under `.cleanxyz/olean/`. `LEAN_PATH` includes that cache, so later proof imports use the compiled modules without placing build artifacts beside checked-in `.lean` proofs.

The top-level JSON shape is:

[source,json]
----
{
  "schema_version": 1,
  "ast": {
    "type": "Module",
    "body": []
  }
}
----

Nodes use a `type` discriminator and fields close to Python's `ast` names. For example, a name expression is `{"type": "Name", "id": "n"}` and a constant is `{"type": "Constant", "value": 1}`.

At the same time, cleanxyz searches for `@cleanxyz:` markers in Python docstrings, and when those are found, it dumps them under `.cleanxyz/tmp.py.reqs.lean` in such a way that unless proof of each requirement is also found, things will blow up when Lean runs.

----
example :
    Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum")
  := Tmp.sum_not_throws

example :
    CleanXYZ.Property.Function.Equiv TmpAst.module "sum" "sum_naive"
  := Tmp.sum_equiv_sumNaive

example :
    Not (CleanXYZ.Property.Function.Throws TmpAst.module "sum_naive")
  := Tmp.sumNaive_not_throws
----

Finally, cleanxyz runs Lean putting everything together:

* `.cleanxyz/tmp.py.ast.json` with the language-neutral AST representation
* `.cleanxyz/tmp.py.ast.lean` with the small JSON-to-Lean import bridge
* `.cleanxyz/tmp.py.reqs.lean` mentioned above with the proof requirements
* `tmp.py.lean` which is supposed to contain your proof
* link:CleanXYZ.lean[] which defines the Python AST representation and properties of the Python language which are then used in correctness proofs
